# Layer 2 실행 루프 프로토콜 v1 (자체 검증 기본 + bkit 선택 증강)

> Coding Agent의 GATE(SKILL.md Layer 2, 7단계)에서 자동 로드된다.
> 루프의 정의: 생성기(Coding Agent)를 검증기에 연결한 것. **병목은 생성기가 아니라 검증기다.**
> 이 문서는 그 검증기를 정의한다.

## 0. 경계

```
Layer 1 Evaluator (evaluator-protocol.md) → 하네스 환경이 잘 만들어졌는가?
Layer 2 검증 루프 (이 문서)               → 하네스 안에서 만든 코드가 좋은가?
```

이 문서의 모든 규칙은 어떤 환경에서든 **bkit 없이 완결 작동**한다.
bkit은 §7의 조건을 충족할 때만 검증기 역할을 증강하는 선택 요소다.

---

## 1. 기본 검증 루프 (모든 환경 공통)

**자가채점 금지.** 코드를 작성한 에이전트가 채점자가 되면 판정이 후해진다.
검증은 생성 에이전트와 **분리된 검증 서브에이전트**(Task/Explore 등 별도 컨텍스트)가 수행한다.

```
[기능 1개 구현 완료 후]
1. 기계 검증 (에이전트 판단 개입 없음):
   a. 전체 테스트 실행 → 전부 통과
   b. 린터 실행 → 에러 0
2. 검증 서브에이전트 호출:
   - 입력: 변경 diff + 관련 설계 문서(docs/) 경로
   - 기준: review-loop.md의 6항목 체크리스트
     (아키텍처·테스트·컨벤션·보안·성능·문서)
   - 출력: Critical / Major / Minor 분류 + 판정(통과 / 수정 필요)
3. 판정 분기:
   - 통과 (Critical 0 + 테스트·린터 통과) → GATE 통과, 커밋 진행
   - 수정 필요 → §4 피드백 가공 → 수정 → 1부터 재검증
     (재검증 반복은 §3 예산에 합산)
```

**종료 조건은 기계가 판정 가능해야 한다.**
"코드가 좋아 보이면"은 종료 조건이 아니다. "전체 테스트 통과 + 린터 0 + Critical 0"이 종료 조건이다.

---

## 2. 실패 출구 (Failure Exit)

무한 재시도는 금지다. 종료 조건에는 반드시 실패 출구가 함께 있어야 한다.

**진전 없음 판정 (둘 중 하나면 즉시 발동):**
- (a) 한 기능에 대한 검증 반복이 예산(§3)을 소진
- (b) 같은 오류 시그니처가 3회 연속 발생 (progress.json attempts 기준, §5)

**발동 시 절차:**
```
1. 재시도 중단
2. 진단 리포트 생성:
   - 막힌 지점 (파일:라인, 실패 단계)
   - 시도 내역 요약 (attempts 각 회차: 무엇을 바꿨고 결과가 어땠는지)
   - 의심 원인 (가설 1~2개, 검증된 사실과 구분 표기)
   - 권고 옵션 2~3개 (예: 설계 변경 / 범위 축소 / 사람 직접 확인)
3. 사용자에게 한국어로 보고 + 에스컬레이션
4. feature-status.json 해당 기능을 blocked로 표기 (passes: true 금지)
```

에스컬레이션 사유 판단은 review-loop.md의 "사람 에스컬레이션 기준" 표를 함께 따른다
(아키텍처 결정·보안·외부 연동·에이전트 간 불일치 등은 반복 소진 전이라도 즉시 넘긴다).

---

## 3. 예산 상한 (Budget Cap)

- **기본 한도: 기능 1개당 검증 반복 5회.**
- Initializer가 progress.json에 `budget.maxVerifyLoops` 로 기록한다.
  프로젝트 특성에 따라 사용자와 합의해 조정할 수 있다
  (Layer 1에서 채점 가중치를 합의하는 것과 동일한 원칙).
- 예산 소진 = "이 길은 막혔다"는 신호다. 실패가 아니라 정보다.
  - 소진 시 **접근 전략 전환 1회** 허용 (다른 구현 방식으로 재설계 후 예산 리셋 1회)
  - 전환 후에도 소진하면 §2 실패 출구 발동
- bkit 증강 모드(§7)에서도 pdca-iterator의 자동 반복은 **이 예산에 합산**된다.
  bkit이 하네스의 예산 상한을 초과해 반복할 수 없다.

---

## 4. 피드백 가공 (Feedback Shaping)

실패를 다음 반복에 넘길 때 스택 트레이스·오류 전문을 통째로 던지지 않는다.
같은 실수로 토큰을 태우는 것은 대개 모델이 아니라 피드백이 거칠어서다.

**3요소로 정리해 전달한다:**
1. **어디서**: 파일:라인, 실패한 단계 (테스트명·린터 규칙명)
2. **직전 의도**: 직전 시도에서 무엇을 하려 했는가
3. **초견/반복**: 처음 보는 오류인가, 이전 시도와 같은 오류인가

반복 오류라면 "이전 시도와 무엇을 다르게 할 것인지"를 먼저 명시한 뒤 수정에 착수한다.
명시하지 못하면 같은 시도의 반복이므로 즉시 §2의 (b) 카운트에 반영한다.

## 5. 외부 기억 (progress.json 확장)

모델은 실행 사이에 잊지만 repo는 잊지 않는다. 시도 이력을 디스크에 남긴다.

```json
{
  "budget": { "maxVerifyLoops": 5 },
  "attempts": [
    {
      "feature": "login-api",
      "try": 2,
      "error_signature": "test:auth.spec:token-expiry",
      "action_taken": "만료 시각 비교 로직을 UTC 기준으로 수정",
      "outcome": "fail-same"
    }
  ]
}
```

- `error_signature`: 오류를 식별 가능한 짧은 서명 (실패 테스트명·린터 규칙·에러 코드)
- `outcome`: `pass` / `fail-same` (같은 오류) / `fail-new` (다른 오류)
- 같은 `error_signature` 3회 → §2 진전 없음 판정 + §6 재발 방지 트리거

---

## 6. 재발 방지 (하네스 강화 루프)

루프는 한 바퀴마다 남는 것이 있어야 한다. 없으면 단순 반복 자동화다.

- attempts에서 **같은 실수 유형이 3회 감지**되면(기능 무관, error_signature 계열 기준),
  에이전트는 재발 방지 규칙 추가를 **사용자에게 제안**한다:
  - AGENTS.md 핵심 불변 규칙에 1줄 추가, 또는
  - 린터 규칙/훅으로 기계적 차단 (가능하면 이쪽 우선)
- 원칙: "AI가 실수하면 탓하지 말고, 그 실수가 다시 안 나오도록 환경을 고친다."
- 제안만 하고 자동 적용하지 않는다 (하네스 구조 변경은 사용자 승인 필요).

## 7. bkit 증강 모드 + 권한 우선순위

### 활성 조건 (둘 다 충족할 때만)

1. bkit 설치 감지: `~/.claude/skills/bkit-rules/SKILL.md` 존재 (Glob)
2. **사용자 opt-in**: "bkit이 설치되어 있습니다. Layer 2 검증에 bkit 에이전트
   (code-analyzer, gap-detector)를 연동할까요?" 를 명시적으로 질문하고 승인받는다.
   **자동 활성화 금지.**

둘 중 하나라도 미충족이면 §1 기본 검증 루프를 그대로 사용한다.

### 활성 시 역할

- code-analyzer / gap-detector가 §1의 검증 서브에이전트 역할을 수행한다:
  - code-analyzer: Critical 0개까지 수정·재검증
  - gap-detector: 설계 문서 대비 matchRate ≥ 90% 통과,
    미달 시 pdca-iterator 반복 (반복은 §3 예산에 합산, 초과 불가)
- §2 실패 출구, §4 피드백 가공, §5 외부 기억은 동일하게 적용된다.

### 권한 우선순위 서열 (상위가 항상 이긴다)

```
1. 사용자 명시 지시
2. 하네스 강제 규칙
   — GATE·검증 생략 금지·잠금 목록·예산 상한·progress.json 스키마
3. bkit 에이전트의 판정·제안
```

- bkit은 **검증·제안 권한만** 가진다. 다음 **잠금 목록**은 bkit 에이전트
  (code-analyzer, pdca-iterator 등)의 제안으로 수정할 수 없다:
  - Karpathy 4원칙 (CLAUDE.md)
  - GATE 정의와 검증 생략 금지 규칙
  - AGENTS.md의 강제 규칙·핵심 불변 규칙
  - progress.json / feature-status.json 스키마
- **판정 충돌 규칙**: bkit 판정과 자체 검증(테스트·린터·검증 서브에이전트) 판정이
  다르면 **더 엄격한 쪽을 적용**하고 사용자에게 보고한다.
  판정 충돌이 반복되면 §2 에스컬레이션 사유다.
- **이식성**: bkit 미설치 PC에서 CLAUDE.md에 bkit 관련 선언이 잔존해도
  no-op으로 무시한다. 존재하지 않는 bkit 스킬·에이전트를 찾으려 시도하지 않는다.
